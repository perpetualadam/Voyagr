## Exact root cause

The old abandonment stage compared serialized route id, destination, geometry,
maneuvers and journey context, then overwrote current with an older checkpoint.
Identical route content was mistaken for the same durable journey. Only the later
promotion compared current with that already-overwritten checkpoint. A different
owner arriving before checkpointing could therefore be erased before the CAS.
Provider route IDs are reusable alternative indices, not unique journey identities.

## Ownership contract

Durable records now have two independent identifiers, generated by Web Crypto from
128 random bits each; no route field, timestamp or checksum determines either:

- `journey_id`: the logical committed journey. New committed journeys receive fresh
  IDs even when route content is identical. Progress updates retain this ID.
- `persistence_owner`: this exact committed write/checkpoint/journal revision. A new
  write receives a new owner; a stale operation cannot update a later revision of
  even the same logical journey.

Application persistence retains ownership observed from its own successful commits
or an explicit owned-record load. It does not look up whichever new owner happens
to exist when an old callback resumes. Abandonment captures and freezes its exact
expected tuple **before awaiting staging**. A continuation/inspection context must
identify that same logical journey. An unrelated unowned plan cannot relabel the
stored journey; restored ownership metadata comes from the durable record, not the
provider route body. This metadata never grants navigation permission.

The existing route database, store and journal remain in use. No competing store
or journal was introduced. All CAS decisions compare exact IDs inside the relevant
atomic IndexedDB read/write transaction. Current writes without an expected owner
can create only into an empty slot; clearing requires an explicit expected tuple.
A new-journey stage captures its prior slot owner once and guards promotion against
that owner. Abandonment additionally requires the tuple captured by its caller
before the asynchronous delegate. Failed identity checks make no checkpoint write.
Identity values/options are copied at invocation, so later object mutation cannot
refresh the expected owner.

## Transaction sequence

1. Confirm deliberate abandonment and capture continuation plus exact ownership.
2. Hold exclusive abandonment ownership, cancel old navigation intent, and stop
   guidance while preserving durable storage. Pending replacement callbacks keep
   their original generation and cannot delete a newer record through stale clear.
3. Inside the staging transaction, check exact expected journey and write owner.
   Only then checkpoint canonical remaining stops with the same journey ID and a
   new checkpoint revision. Record the independently owned inert pending entry.
4. Promotion checks the exact checkpoint tuple. The owned journal exposes the
   previous journey to readers while finalization is pending.
5. Finalization checks the exact journal tuple and writes a minimal tombstone:
   `id`, `journey_id`, `persistence_owner`, `abandoned`. It contains no route data,
   geometry or continuation and is not a navigation candidate.
6. Retire memory only after durable finalization. Final status/display failures
   cannot roll back a completed retirement while leaving memory retired.
7. Rollback restores only this journal's previous checkpoint, or recognizes that
   exact checkpoint as unchanged. A different owner is never overwritten. When
   restoration/ownership cannot be proven, enter RECOVERY_REQUIRED and block fresh
   live starts rather than silently adopting current storage.

Repeated retirement is idempotent for the captured logical journey; an old expected
revision cannot clear a later tombstone or newer journey. A new writer that commits
*after* retirement finalization survives the old completion. This is a valid later
operation, not grounds to retroactively overwrite it during rollback.

Normal progress saves retain the logical journey ID and change the write owner.
Planning/live promotion publish their committed journey ID to the UI context only
after success. Canonical continuation comparisons still check identity, ordered
intent, progress index and unavailable state; ownership metadata is checked by CAS,
not mistaken for physical progress. Provider/route data does not carry storage
authority. Legacy or mismatched inspection contexts cannot supply ownership evidence.

## Reload, legacy and compatibility behavior

An atomic read returns logical saved state and raw durable ownership together.
After interrupted abandonment, the logical previous journey and raw journal have
the same journey ID: a fresh session can inspect and explicitly retire that exact
observed owner. Saved route payloads remain inspection-only and preserve canonical
completed-stop continuation. Tombstones return no visible current journey.

A pending replacement belonging to a *different* logical journey is not silently
adopted as ownership of its visible predecessor. Legacy records missing either
reliable identifier remain inspectable, but identity-sensitive mutation refuses.
There is no automatic ownership backfill, forced deletion or route-content-based
migration. Legacy/unresolved records may therefore require a separately reviewed,
explicit reset/migration or recovery workflow; reloading alone cannot manufacture
missing ownership evidence. No such reset or migration was performed here.

Current mode/lifecycle/renderer paths require the durable-ownership service contract;
cached older peers cannot silently bypass it. Updated source URLs and worker v51
carry the changed modules. Fully old installed clients still require an update;
real worker scheduling and device acceptance remain untested.
